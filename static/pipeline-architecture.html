3

우선순위 점수 산출

priority_scorer.py — 학교 단위 점수 계산

4개 항을 조합하여 학교별 종합 점수를 산출하고, 상위 3건을 "오늘의 검토 후보"로 선정한다.

S = 3 × max(★) ← 최고 별 등급 (최대 9) + 2 × Σ(카테고리 가중치) ← C3=3, B1/C1/C2/F1=2, D2/E2/C5=1 + 5 × R ← 3년 반복 여부 (0 or 5) 카테고리 가중치 (맥락적 심각도): C3(학생 안전) = 3 ← 미조치 피해, 학생 보호 직결 B1/C1/C2/F1 = 2 ← 급변동, 항목 연동, 교차검증 D2/E2/C5 = 1 ← 통계적 참고, 미갱신 의심 + 3 × P ← 실제 사례 패턴 (0 or 3)
Top 3 결과 1위 A고 23점 (4개 카테고리)
2위 B고 23점 (4개 카테고리)
3위 C고 22점 (5개 카테고리)

03레이어 4 상세: 대화형 탐색 내부 흐름

자연어 질의가 분석 보고서로 변환되는 내부 5단계 과정. 기존 Text-to-SQL 도구와 달리, 교육 공시 도메인 지식이 모든 단계에 주입된다.

A

질의 분석 (Query Understanding)

LLM이 사용자 질문에서 의도, 대상 컬럼, 분석 유형을 추출한다.

"학교 교원이랑 학생 수 비교했을 때 비이상적으로 늘어나는 거 있어?" → 의도: 비교 분석 (두 변수 간 관계) → 대상: teacher_count, student_count → 유형: 방향 불일치 탐지 (역방향 변동) → 매칭 룰: C1-1 (학생↔교원 연동)
범용 챗봇과의 차이 일반 Text-to-SQL은 컬럼명을 사용자가 정확히 알아야 한다. 우리는 "교원"이라는 자연어를 teacher_count, 정규교원, 기간제교원 등 관련 컬럼으로 자동 매핑하고, 기존 룰셋(C1-1)과 연결하여 적절한 분석 기준을 자동 적용한다.
B

분석 계획 수립 (Plan Generation)

LLM이 JSON 형태의 분석 계획을 생성한다. 어떤 컬럼을, 어떤 기준으로, 어떻게 비교할지를 구조화한다.

{ "columns": ["school_name","year","student_count","teacher_count"], "criteria": "전년대비 변동률 방향 불일치", "threshold": "C1-1 기준: 변동 방향이 반대", "comparison": "동료군(같은 구, 같은 설립유형) 평균", "pandas_code": "result = df.groupby('school_code').apply(check_direction)...", "normal_exceptions": ["학과 개편","교육통계 연계 항목"] }
C

안전 실행 (Sandboxed Execution)

생성된 pandas 코드를 화이트리스트 기반 샌드박스에서 실행한다.

🛡️
화이트리스트

허용된 함수만 실행 가능: groupby, filter, query, describe, mean, median 등

🚫
금지 패턴

import, exec, eval, open, os., sys., subprocess, __ 등 차단

📋
읽기 전용

DataFrame 복사본에서 실행. 원본 데이터 변경 불가

⏱️
타임아웃

실행 시간 5초 제한. 무한루프 방지

D

결과 해석 (Report Generation)

pandas 실행 결과를 LLM이 받아서 구조화된 보고서로 변환한다.

보고서 구성 ① 확인한 컬럼 목록
② 적용한 수치 기준과 근거
③ 탐지 결과 (이상 학교 리스트)
④ 실제 데이터값 vs 비교군
⑤ 자연어 해석 + 맥락 설명
⑥ 신뢰도 표시 (높음/중간/낮음)
⑦ 정상 예외 해당 여부
E

후속 탐색 제안 (Guided Follow-up)

분석 결과에 기반하여 다음 탐색 방향을 자동 제안한다. 기존 세션의 맥락을 유지하여 점진적으로 심화 탐색이 가능하다.

제안 유형 필드 확장: "급식비도 추가해서 볼래"
범위 변경: "강남구만 따로 볼 수 있어?"
시간 변경: "A고 3년 추이 보여줘"
룰셋 연동: "이 학교 전체 룰 점검 결과 보여줘"
패턴 매칭: "이 패턴이랑 비슷한 학교 더 있어?"
세션 패턴 종합 사용자가 여러 질문을 던지면, 각 결과의 주제(학폭, 교원, 재정 등)를 자동 추적하여 MC-1~MC-13 맥락 패턴과 매칭한다. "지금까지 탐색 결과를 종합하면 MC-1(학교 분위기 악화) 패턴과 유사합니다."

정상 예외 16가지 (LLM 정상 사유 태깅)

탐지 후 LLM이 정상 사유 후보로 제시 — llm_interface.py

아래 16가지 상황에서는 이상 탐지가 되더라도 정상일 가능성이 있다. 코드로 자동 판별이 어려운 항목은 LLM이 "정상 사유 후보"로 함께 제시하여 담당자가 판단한다.

#정상 예외대상 룰처리 방식
1신설/폐교/통폐합/분교-본교 전환전체LLM 사유 태그
2학급 감축·증설 정책 적용 연도C1, B1LLM 사유 태그
3학과 개편/고교학점제 전환C1, C5LLM 사유 태그
4남녀공학 전환C5LLM 사유 태그
5자료기준일이 항목 간 다른 경우전체LLM 사유 태그
6학폭 공시연도 ≠ 사안 발생 연도B1-6, C3-3LLM 사유 태그
7급식비 입력단위 '천원' 미준수C2-3LLM 사유 태그 + C2-3+ 극단값 분리
8기준일 차이 코호트 산술 오차C5-1임계 완화 (-7%~+3%) 반영
98월 확정 후 SR 수정 한쪽 반영F1'LLM 사유 태그
10보직교사 1교사 1직위 규칙C1-5LLM 사유 태그
11교육통계 연계 14개 항목 수정 불가E2, F3E2 대상에서 연계 항목 제외
12교원 연계 제외 규칙F1', F3강사 보정 공식에 반영 (I단계)
13가해학생 조치 미실시 → 가해수 미포함C3-3자동 필터 (등급X 제외)
14자동 제외 (신설학교 전년도)E1LLM 사유 태그
15교육청별 증감기준 자체 설정B1B1-1 ★★ 하향으로 반영
16졸업생 진로현황 집계 범위 차이F1'LLM 사유 태그
설계 원칙 16가지 중 코드로 자동 필터 가능한 것(#8, #11, #12, #13, #15)은 사전 보정 또는 자동 필터로 처리한다. 나머지 11가지는 외부 정보(정책 변경, 학교 특성 등)가 필요하므로, LLM이 탐지 결과와 함께 "이런 정상 사유가 있을 수 있습니다"라고 태그 형태로 제시한다. 최종 판단은 항상 담당자의 영역이다.

04기존 도구 대비 차별점

범용 Text-to-SQL 도구(Chat2DB, BlazeSQL, Vanna.ai 등)와 비교한 핵심 차별점. "도메인 특화 + 룰셋 연동 + 맥락 해석"이라는 조합은 기존 제품에 없다.

기능 범용 Text-to-SQL EduData Watch
도메인 지식 없음 (스키마만 읽음) 매뉴얼 986p + 룰셋 25개 + 정상 예외 16개 사전 탑재
분석 기준 사용자가 직접 지정 v3 룰셋 기준 자동 적용 (3축 기반 별 등급)
비교군 사용자가 직접 설정 동료군(같은 구, 같은 설립유형) 자동 매칭
결과 해석 SQL 결과 테이블만 반환 자연어 해석 + 정상 사유 추론 + 확인 질문 생성
후속 조치 없음 "자체점검표 p17 확인 대상" 등 구체적 안내
우선순위 없음 4항 점수 공식 + "오늘의 3건" 자동 선정
패턴 감지 없음 MC-1~MC-13 맥락 패턴 자동 매칭
이상치 맥락 통계 수치만 인과 방향(학생→학급→교원) 기반 맥락적 이상 감지
False Positive 관리 없음 16개 정상 예외 자동 필터 + LLM 사유 추론

05학술적 근거

파이프라인 설계의 학술적 기반. 각 레이어의 접근 방식이 최신 연구에 의해 뒷받침된다.

AnoLLM (ICLR 2025)

LLM 기반 표형 데이터 이상치 탐지. 기존 11개 방법 대비 SOTA 달성 (AUC-ROC 0.810). 레이어 3의 LLM 활용 근거.

CausalTAD (arXiv 2025)

인과관계 기반 컬럼 배치 시 이상치 탐지 정확도 +9.1%. C1 룰(학생→학급→교원 인과 방향)의 직접적 근거.

CMS Auto DQM (arXiv 2501)

"A threshold too low will trigger too many false positives." Alert Fatigue 방지를 위한 우선순위 시스템의 근거.

Atlanta Cheating Scandal (2011)

통계적 이상 패턴이 교육 데이터 부정을 최초로 밝혀낸 선례. 44개교 178명 적발. 맥락 탐지의 현실적 가치.
